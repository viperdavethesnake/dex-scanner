## Changes Made

### 1. Filter: Allow Solana `recovering` when `vol_trend = rising`

**Node:** Build Prompt — hard pre-filter block  
**Before:**
```javascript
const microPass = chain === 'solana'
  ? (micro !== 'recovering' && micro !== 'down' && micro !== 'flat')
  : (micro !== 'recovering' && micro !== 'down');
```
**After:**
```javascript
const microPass = chain === 'solana'
  ? ((micro !== 'recovering' || item.json.volTrend === 'rising') && micro !== 'down' && micro !== 'flat')
  : (micro !== 'recovering' && micro !== 'down');
```

**Rationale:**  
ML pattern mining on 25,887 scanner-window rows found `recovering + rising vol + VL 4–8x` on Solana has **29.9% moonshot rate, 2.33x lift** (n=67). The original `recovering` exclusion was set using aggregate stats (recovering = −2.57% avg, 40.3% win). The ML reveals that aggregating across all vol_trend values masks a real subgroup — when volume is already rising into the recovery, the token is often resuming momentum rather than bleeding out. Avg outcome for this specific combo is +3.94%, which is positive on a chain where the overall average is −1%.

**Expected impact:** Admits a small new cohort of Solana tokens per scan (estimate: 1–3 per batch). The LLM will see them; the hard filter no longer excludes them. False positives in this cohort will be caught by the LLM's conviction sizing.

**Validation:** Monitor via collector — look for `recovering` Solana tokens with `volTrend=rising` outcomes over the next 2 weeks.

### 2. New Signal: `liq_mcap_ratio` in Prompt

**Node:** Build Prompt — per-token prompt line  
**Added:** `Liq/MCap: {ratio}x` field surfaced in the token data block for every token.

**Rationale:**  
`liq_mcap_ratio` ranked **top-5 on both chains** across all target thresholds in the ML model (gain score: 1,979 on Base moonshot, 6,485 on Solana moonshot). It represents liquidity / market cap — a low ratio means the pool is thin relative to the token's implied size, which historically precedes explosive moves. This ratio was computable from existing normalized data but never surfaced to the LLM.

**Formula:** `liquidity_usd / market_cap`  
Low (<0.3) = high explosion potential. High (>1.0) = deep pool, lower volatility.

### 3. New Signal: `momentum_score` in Prompt

**Node:** Build Prompt — per-token prompt line  
**Added:** `Momentum score: {value}` field when computable.

**Rationale:**  
`momentum_score` ranked top-10 on both chains for moonshot prediction (gain: 1,347 Base, 5,087 Solana). It combines price velocity and volume acceleration into a single number the LLM can anchor on.

**Formula:** `price_ch_5m × min(volume_5m × 12 / volume_1h, 10.0)`  
Positive and large = price moving up on accelerating volume. Negative or near zero = momentum absent or diverging.

## Changes NOT Made (and why)

### Base VL ceiling above 8× for `fading` micro-trend

ML found `fading + flat vol + VL >8x` on Base has 38.2% moonshot rate (89 tokens, 2.22x lift). However:
- The existing pipeline doc's own empirical tables don't break down Base outcomes above 8x in enough detail to verify this is stable across the full dataset.
- The n=89 sample is meaningful but not large enough to override a hard filter rule with significant blast radius.
- Action: Add a `vl_ratio` field to the prompt so the LLM can see when VL is >8 on passing tokens and factor it into reasoning. Hard filter unchanged until 4+ more weeks of data accumulate.

### Any change to Base `recovering` exclusion

ML did not find a sub-combination of `recovering` on Base with a clean positive moonshot signal. Existing table shows recovering on Base = +2.31% avg but 53% win — positive but not directionally strong enough to justify an exception. Keep excluded.

### GoPlus/Birdeye enrichment timing fix

GoPlus and Birdeye columns in collector have <1% fill rate for scanner-window tokens — data arrives after tokens age past the 90-minute window. This is a collector-side fix requiring re-architecture of the enrichment timing (enrich at ingest, not lazy). Not addressed in this tuning pass. Tracked as future work.

### Separate model score as a pre-filter

The ML moonshot models (AUC 0.74 Base, 0.71 Solana) could theoretically replace or augment the current hard filter. Not implemented now because:
1. Requires model deployment (inference at scan time, not just training)
2. The hard filter's transparency is valuable — the LLM, operator, and PIPELINE.md all reference it
3. Start by surfacing `liq_mcap_ratio` and `momentum_score` in the prompt; if LLM performance improves, revisit scoring
